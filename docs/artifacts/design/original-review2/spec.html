Intent and release boundaryTop

Make codeArbiter’s specifications and implementation plans consistent enough for machines to validate and pleasant enough for people to review. The agent writes domain content; a shared Go binary owns the two schemas, identity, selective extraction, safe mutation and rendering.

The caller is the existing codeArbiter feature/sprint workflow, not a new command or a new agent. The human continues to request a feature and review the resulting spec and plan through the current workflow. The files can also be opened directly in a browser.

Symbols, selective reads and canonical hashingTop

Artifact IDs remain stable across file renames. The resolver scans approved artifact locations and verifies the embedded ID; a path is a locator hint, not authority. More than one live candidate for an artifact ID, including a Git merge duplicate, yields AMBIGUOUS_ARTIFACT and blocks dependent execution. A filename move may update presentation locators and model hashes, but does not rewrite criterion identities or normative plan binding. Record IDs are immutable and not recycled; retirement leaves a rendered tombstone with a reason and optional replacement ref.

Each addressable record is rendered once inside a generated CA:BEGIN / CA:END marker pair and an element carrying the same ID. Extract the model by ID, not by line number, heading text, array offset or marker-only heuristics. The HTML parser validates marker correspondence and nested pairing; user strings never become trusted markup.

<!-- CA:BEGIN:AC-009 -->
<article id="AC-009" data-ca-symbol="AC-009" data-ca-kind="criterion">
  ... generated content ...
</article>
<!-- CA:END:AC-009 -->

Go html/template strips literal HTML comments. Emit structural marker comments through a small trusted writer accepting only validated identifiers; escape all ordinary content. The reference renderer includes markers so their preservation is testable.

Approval, task state and stale evidenceTop

Allow DRAFT → READY → APPROVED → SUPERSEDED, with readiness derived from validation and approval checked against the exact normative hash. DRAFT may be incomplete; READY requires no unresolved blocking decision and complete applicable contracts/relationships. The existing feature user gate and sprint SMARTS decision remain the policy authorities. A document record reports workflow attestation and its source; it is not a cryptographic proof of a human identity.

Sources: SRC-01

The workflow adapter records approved content only after its existing authorization and audit steps. Generic apply cannot create approvals, set APPROVED, mark tasks ACCEPTED or fabricate evidence. If a source is unavailable or cannot be bound, report AUTHORITY_UNVERIFIED and block execution rather than turning a self-declared flag into authority. Existing same-user filesystem limitations are explicit; this is not a sandbox against an arbitrary local writer.

On resume, first validate authority, spec/plan bindings and outstanding recovery records. Within one active checkpoint scope, a dependency in REVIEW with successful spec review and fresh task verification may unblock the next task provisionally. Across scopes, dependencies must be ACCEPTED and applicable evidence current. REVIEW is never completion, export eligibility or release authority. IN_PROGRESS after interruption returns reconciliation; verified REVIEW work can resume within its same scope after revalidation. Never restart approved framing merely because verification must be rerun.

Ordinary task state changes do not mutate the plan’s normative definition. A normative plan edit invalidates plan approval. Rebinding to a changed specification is explicit and does not silently regenerate wording, dependencies, verification commands or historical acceptance.

Each checkpoint is an execution scope. Scope entry validates external dependencies and records the starting tree. Tasks move PENDING → IN_PROGRESS → REVIEW after task-level spec compliance and fresh verification. Same-scope dependencies may use REVIEW only on that recorded tree lineage. After all members reach REVIEW, reverify the entire scope against one final verification-input fingerprint and run the existing combined-diff quality review. accept-scope atomically records acceptance for all members or none, through the recovery-aware authority adapter. Failed review returns affected tasks to work and invalidates dependent provisional results. This explicitly repairs the old accepted-dependency/whole-scope-review ordering conflict without skipping quality review.

Sources: SRC-06

A later source change makes applicable verification stale; it does not erase historical completion or force reimplementation. Revalidation reruns the relevant checks and binds a new receipt to current inputs. A normative spec/plan change instead requires reviewed rebind/reapproval. State-only, presentation-only and exact evidence-output writes leave the verification-input fingerprint unchanged. Final checkpoint and commit handoff still require all applicable checks current at the final snapshot.

Checkpoint ordering is explicit. A checkpoint cannot depend on a later checkpoint, and task selection cannot cross an unaccepted earlier checkpoint. Bootstrap tasks may define the format, but implementing the engine must not depend on the engine already enforcing its own plan: use the current approved workflow for this one bootstrap implementation, then exercise the new path in isolated fixtures before cutover.

Storage, safety and renderingTop

For each mutation: resolve the repository and trusted artifact path; acquire a bounded per-artifact writer lock; read and validate the current file; compare revision and model hash under that lock; validate the proposed complete model; render to a same-filesystem temporary file; verify the staged bytes; replace through a platform-tested primitive; then release the lock. Lock contention returns a conflict; never automatically steal a lock based only on wall-clock age.

Guarantee no lost update among cooperating writers and no partial canonical HTML after a supported single-file replacement. Distinguish process interruption from power-loss durability. Native platform tests and an explicit recovery record must support any durability claim. Do not assume ordinary rename gives identical Windows and Unix guarantees. Network filesystems and mixed-runtime shared working trees are not promoted by this feature.

Approve/cutover operations may touch an artifact plus an audit/index record. Do not claim a multi-file transaction from a single-file rename. Stage a bounded intent/recovery record with exact old/new hashes; incomplete state blocks execution and exposes a read-only recovery report until reconciliation. Ordinary reads must not execute recovery or make hidden writes.

Reject traversal, absolute repository-escape paths, symlink/reparse-point escapes, ambiguous identifiers and unsafe asset references. Never trust a binary resolved from the target repository or arbitrary PATH. Trusted package resolution and its existing installation boundary select the executable. The binary does not make network requests, load remote schemas or run commands stored in a plan.

Render a real static document, with the retrieved codeArbiter logo by default. Repository branding may provide a display name and a local PNG/JPEG or strictly validated inert SVG. No remote images, executable SVG, scripts, arbitrary templates or stylesheet injection. Embed the sanitized result, CSS and model so the document is portable and works offline. Escape JSON for the HTML script-data context so a literal closing script tag cannot escape the model container.

Sources: SRC-13

Use semantic headings, keyboard-accessible native disclosure, visible record anchors, light-background body text and print rules. Test 390 px and 1440 px viewports, 200% text zoom, long identifiers and code blocks. Layout may scroll a code/table container horizontally, but no element may overlap or escape its container. No font files or external font dependencies are shipped.

Do not promise that every post-replacement I/O error means no mutation. Before replacement, validation/conflict failure leaves bytes unchanged. After replacement, an audit/receipt/fsync failure is COMMIT_OUTCOME_UNKNOWN or RECOVERY_REQUIRED and returns the operation ID plus known identities. Retries inspect the recovery record instead of blindly applying the mutation again. A bounded operation ID and old/new hashes distinguish an acknowledged repeat from a new request.

A model names only a supported, package-owned renderer version and stylesheet digest. Unknown renderers yield UNSUPPORTED_RENDERER, not RENDER_DRIFT or silent reformatting. Upgrades preserve old readers or require an explicit reviewed presentation migration. Git conflicts or competing model containers are invalid until reviewed resolution; never auto-merge array positions or mint replacement IDs to conceal conflicts.

Reference rendering must show actual obligation labels, blockers, tombstones and task states. It must not hard-code MUST, PENDING, zero accepted tasks or absence of open decisions. A displayed approval state is labeled recorded and authority-unverified until the coordinator checks the external authority source. Custom branding changes title and visible brand label as well as the logo; provenance remains available separately.

Proposed design decisionsTop

These choices define the draft under review. They are not yet accepted architectural decisions in the repository.

DEC-01 · PROPOSED

Interaction surface

Choice: Use existing governed EXEC/Bash tools and existing feature/sprint/plan routines. Load a small artifact-protocol leaf only when those routines need it.

Reason: The proposed human-facing command only duplicated create/read/edit convenience already reachable in existing workflows.

DEC-02 · PROPOSED

First release boundary

Choice: Ship specs and implementation plans together; preserve all downstream consumers in the same rollout.

Reason: Plan criteria references, execution state and resume are part of the first complete behavioral path.

DEC-03 · PROPOSED

Canonical representation

Choice: One HTML file per artifact, containing one authoritative JSON model and a deterministic static rendering.

Reason: No editable JSON/Markdown sidecar; temporary request files and derived farm projections are explicitly non-authoritative.

DEC-04 · PROPOSED

Semantic ownership

Choice: Specs own criteria; plans reference them and own tasks. Evidence/approval sources remain owned by current governance.

Reason: Avoid independently rewritten acceptance ledgers and a second approval system.

DEC-05 · PROPOSED

Identity and integrity

Choice: Immutable artifact/record IDs; separate document revision, normative digest and full model digest.

Reason: Cosmetic changes and task status updates must not masquerade as requirement changes; actual contract changes must not retain approval.

DEC-06 · PROPOSED

Change concurrency

Choice: Document-level compare-and-swap with a writer lock and full-model hash; no automatic fine-grained merges in v0.1.0.

Reason: Sequential revisions alone do not distinguish divergent branches or hand edits. A lock plus hash check prevents cooperating writers from losing updates.

DEC-07 · PROPOSED

Stale execution

Choice: A changed spec or normative plan blocks new dispatch. Explicit reviewed rebind conservatively marks prior task evidence stale.

Reason: Do not carry ACCEPTED state across a changed contract by assuming a dependency graph proves unaffectedness.

DEC-08 · PROPOSED

Drafts and previews

Choice: Permit structurally valid partial drafts. A draft plan may be produced explicitly for review, but cannot execute until its spec and plan approvals are current.

Reason: This package is a requested planning preview, not an exception to implementation gates.

DEC-09 · PROPOSED

Readable delivery

Choice: Self-contained static HTML is the canonical output in v0.1.0; use one renderer/style source, embedded per file.

Reason: Removes broken local assets and the need for an extra save-as-single-file command. Runtime branding changes do not affect normative hashes.

DEC-10 · PROPOSED

Trust boundary

Choice: Treat repository spec/plan text and commands as untrusted data. The binary never executes verification commands or model text.

Reason: Existing governed execution performs tests; a file-local approval record is a workflow attestation, not cryptographic identity proof.

DEC-11 · PROPOSED

Native distribution

Choice: Package reviewed binaries; end users do not install Go or fetch dependencies during artifact operations.

Reason: Pin build inputs. Report native tested cells separately from cross-compiled artifacts; preserve existing native-platform support before default rollout.

DEC-12 · PROPOSED

Task granularity

Choice: Bound tasks by a verifiable concern, exact paths, dependencies and observable completion; do not invent a universal 2–5-minute duration.

Reason: The current task-duration rule is a workflow heuristic, not evidence of an optimal plan schema. This release changes that wording explicitly.
