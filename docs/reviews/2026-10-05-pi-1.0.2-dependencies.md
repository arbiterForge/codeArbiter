Reviewed 2026-10-05 under ADR-0035/ADR-0041 and the `ca-add-dep` dependency
reviewer contract. The independently reviewed graph is an external build/CI
host prerequisite; Pi and its dependency bytes are not distributed in the
adapter payload.

  the registry `gitHead` and root npm provenance attestation.

  `c7c7594880a3db9bbf2dd510a684d3b211bb225796bdb7b20952e8148bc7ebb3`.

- Graph: 147 entries; every package's exact version, registry URL, integrity,
  license and runtime dependency fields independently matched to npm metadata.

- Licenses: MIT (87), Apache-2.0 (36), BSD-3-Clause (13), ISC (7),

The npm tarball no longer publishes `npm-shrinkwrap.json`, as documented in
[v1.0.1](https://github.com/earendil-works/pi/releases/tag/v1.0.1).
Capture preserves a published shrinkwrap when present. Otherwise it reads the
upstream managed-install lock only at the exact registry source commit, binds
its Pi entry to the integrity-verified tarball and runtime manifest, and checks
every transitive entry against exact registry metadata. The pre-publication
lock omits root integrity; capture supplies it only from the verified tarball.
It performs no npm resolution, install, lifecycle hook or candidate execution.
The output stays `PENDING_REVIEW` until independent dependency review and
signature/provenance evidence admit the strict `PASS` receipt. Supported
installation retains isolated configuration, clean prefix, disabled scripts,
`npm ci`, fresh audits and signature/provenance verification.

The only `brace-expansion` is 5.0.12. The three retained advisories have patched
5.x floors of [5.0.12](https://github.com/advisories/GHSA-q2hr-2g5m-vwhr),
[5.0.11](https://github.com/advisories/GHSA-qhr7-859c-m2p7) and
[5.0.10](https://github.com/advisories/GHSA-6j4f-fj2g-mc7p). The current receipt
has no accepted advisories. Historical receipts and their rejection tests are
retained as evidence; the supported-version allowlist cannot install them.

This dependency PASS does not prove runtime compatibility or EOF shutdown.
Required PR CI owns the live Windows/macOS/Linux qualification at the final
commit. The draft PR records those results separately; release notes make no
claim that 1.0.2 fixes the previously observed Windows RPC EOF defect.
