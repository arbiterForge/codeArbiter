# ADR-0029 — Publish ca-pi to npm under the arbiterforge org alongside pinned Git tags

## Status
Accepted — decided by SUaDtL@users.noreply.github.com on 2026-08-09 ("i'd like to start
publishing to NPM in the arbiterforge organization"; "adr for change to publishing route
approved"). The org actions secret `NPMJS_TOKEN` was created by the owner the same day.

## Context

Since ADR-0013, ca-pi has distributed exclusively as a pinned Git tag
(`pi install git:github.com/arbiterForge/codeArbiter@ca-pi-v<version>`); `tech-stack.md`,
`coding-standards.md`, and `docs/parity.md` all recorded "no npm release / npm packaging is
future work", and `docs/parity.md` carried a "Pi npm package | DEGRADED" exception row. Pi's
native discovery and install channel is npm (`pi install npm:<name>`), so the Git-only posture
kept ca-pi invisible to the ordinary Pi extension-discovery path and made every install
instruction carry full Git coordinates.

## Decision

Each `ca-pi-v*` release is additionally published to npm as **`@arbiterforge/ca-pi`** by a
tag-triggered GitHub Actions workflow using the org `NPMJS_TOKEN` secret and npm provenance
(GitHub OIDC, `id-token: write`). The published artifact is the SAME repo-root package the Git
install serves — the root manifest stays generated by `tools/build-host-packages.py` from the
nested `plugins/ca-pi/package.json` (single source, ADR-0011 discipline), gaining a `files`
whitelist and `publishConfig {access: public, provenance: true}` and losing `private`. The
pinned Git tag remains the reproducible-pin channel and the evidence anchor; npm is the
convenience channel. `ca`, `ca-codex`, and `ca-sandbox` are NOT published to npm — their hosts
install from marketplaces, and extending npm publishing to them requires a new decision.

## Alternatives considered

- **Stay Git-only** — keeps the recorded posture but leaves ca-pi invisible to Pi's native
  `pi install npm:` discovery path; rejected by the owner's explicit directive.
- **A separate npm-specific package tree** — would fork the payload that ADR-0011's byte-identity
  discipline exists to keep single-sourced; the Git package and npm tarball would drift.
- **Manual local `npm publish` by the maintainer** — no provenance attestation, token handling on
  a workstation, and no tag-version guard; CI publishing is strictly safer and reproducible.
- **Unscoped `ca-pi` npm name** — outside the org the token belongs to, squattable, and carries
  no org trust signal; the scoped name matches the granted token's authority.

## Consequences

- The "no npm release" clauses in `tech-stack.md`, `coding-standards.md`, and `docs/parity.md`
  are superseded by this ADR; the doc-contract tests pinning the old posture are repointed to
  pin the new one. `docs/parity.md`'s "Pi npm package" exception row flips DEGRADED → SUPPORTED.
- Install documentation gains `pi install npm:@arbiterforge/ca-pi` as the convenience path while
  keeping the pinned Git tag as the reproducible pin.
- The npm package page shows the monorepo README (accepted for v1; a package-specific README is
  future polish, not a blocker).

## Risks

- A compromised `NPMJS_TOKEN` could publish a malicious version. Mitigations: provenance ties
  every tarball to a public CI run on this repo; the workflow triggers only on `ca-pi-v*` tags,
  which only the release lane creates; the token lives solely as an org actions secret, never in
  the repo or a prompt. A rotation invalidates the channel without touching Git installs.
- A mistagged ref could publish a wrong version — the workflow's tag/manifests version guard
  fails the job before `npm publish` runs.
- npm outages or unpublish policy changes affect only the convenience channel; the Git path is
  unaffected, which is why it remains the evidence anchor.
