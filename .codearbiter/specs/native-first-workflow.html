Native-first enrollment and work-bound workflows

Enroll new HTML projects with one portable native work owner and bind actionable feature, fix, and sprint outcomes to durable work IDs without duplicating spec, plan, check, or provider authority.

Intent

INTENT-01

Intent

CallerUser-supplied next handoff
OutcomeEnroll new HTML projects with one portable native work owner and bind actionable feature, fix, and sprint outcomes to durable work IDs without duplicating spec, plan, check, or provider authority.
ProblemNew HTML enrollment creates legacy boards, while first native work creation can mint divergent project IDs in separate clones. Feature, fix and sprint routes do not consistently retain one work identity.

Approach

Binding decision refs

AC-003

Project identity stable before first work

must
Applicability
Modeunconditional
RationaleRequired for this native-first increment; no new authorization gate.
Guarantees
  • `work/project.json` is **engine-owned portable state**, not a Python-written shell of one. A newly selected native project gets one stable project identity as part of completed enrollment, before independent branch/worktree first-work creation can mint contradictory project IDs. Prefer factoring the existing native project-identity allocation into the **existing initialization transaction** or one minimal idempotent engine operation. The choice must work on fresh clones, Windows, and a retried interrupted scaffold. Do **not** mint a dummy work item to get a project ID; do **not** derive identity from a mutable title, local absolute path, or a token from a machine-local transaction journal.

SEC-SMARTS

SMARTS design rationale

Blocks

Alternatives: create project identity in knowledge-initialize, or add a separate bootstrap operation invoked during scaffold.

LensKnowledge initializationNew bootstrap operation
ScalableIndifferent. Both store one project JSON file.Indifferent. Both store one project JSON file.
MaintainableStrong. Reuses the current initialization operation.Adequate. Adds a protocol verb and scaffold caller.
AvailableStrong. Scaffold remains usable before native payload invocation.Weak. Scaffold requires the native payload immediately.
ReliableStrong. Marker and project ID commit atomically.Adequate. Separate scaffold and native transactions need recovery.
TestableStrong. Existing knowledge fixtures cover the transaction.Strong. A distinct bootstrap operation has deterministic fixtures.
SecurableAdequate. Existing bounded writer and store checks apply.Adequate. Same store checks apply to a new operation.

Decisive lenses: Maintainable, Available and Reliable favor knowledge initialization. Scalable, Testable and Securable do not differentiate materially.

Weak and Unknown: the separate operation has a Weak availability fit because /init would require the native payload before context population. No decision-critical Unknown remains.

Assumption: actionable work creation from an incomplete HTML scaffold can refuse until knowledge initialization; the marker and project identity then share a commit.

Non-SMARTS: this keeps the implementation small and avoids a new installed-host operation contract.

Priority evidence: the user-supplied packet prefers the existing initialization transaction when it is coherent. Recommendation: knowledge initialization, strong.
