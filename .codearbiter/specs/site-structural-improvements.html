Site structural improvements: one page per workflow, captured examples, one teaching layer

Readers get one reference page per workflow with a fixed shape and a drift check, guide examples captured from real deterministic tool runs, and guides and Academy lessons that link to each other instead of teaching twice.

Intent

INTENT-01

Intent

CallerA codeArbiter documentation reader choosing, running or learning a workflow, and the maintainer who keeps the docs true.
OutcomeEach workflow has one reference page with the same reader shape and a build-time drift check. Guide examples of deterministic tool output render from captures bound to their source. Each task is explained once in the guides, and guides and lessons link to each other.
ProblemThirteen commands each have a separate skill page with separately written text, so a reader needs two pages for one workflow and they can disagree. Skill pages have no examples, and nothing checks hand-written reference text against the source it describes. Guides show system behaviour only in hand-written examples; the one captured run is the landing hook replay. Guides and Academy lessons cover the same tasks with no links between them, and lessons re-explain what the guides explain.
Source refsNone recorded

Decisions

DEC-01

Which URL survives a merge

Authorityproposed
ChoiceCore and advanced commands: the command URL is canonical and the merged skill URL redirects to it. Alias commands: the skill page is the workflow page and the alias page stays a short pointer.
RationaleReaders type core and advanced commands; alias commands send readers elsewhere (pr --cleanup, status drift, init --brownfield, init --greenfield), so their procedure cannot live on a page the docs tell readers not to use. Redirects keep old URLs working.
Source refNot yet supplied
DEC-02

Where pairs come from

Authorityproposed
ChoiceDerive pairs from the shipped command source naming its owning skill as its first heading; an ambiguous or unknown name fails generation.
RationaleAll 13 pairs follow that convention today; a hand-kept list would be one more thing to drift.
Source refNot yet supplied
DEC-03

How reader fields are stored

Authorityproposed
ChoiceShort reader fields (use, avoid, asks, produces, runs inside) in curated frontmatter, validated by load-curated; examples stay in the body under a required Example heading.
RationaleThe loader already validates gates and related lists in frontmatter. 31 command files already have an Example section in the body, and moving code blocks into YAML would make them harder to edit.
Source refNot yet supplied
DEC-04

How captures stay fresh

Authorityproposed
ChoiceCommit captures as assets with sha256 for the entry script and every in-repository module it loaded; npm run gen fails on a mismatch with the working tree; refresh with npm run capture. The landing hook proof keeps its existing binding.
RationaleSame shape as hook-proof.json with no new CI execution step. Hashing loaded modules, not just the entry script, keeps the load-bearing assumption true when a shared hook library changes.
Source refNot yet supplied
DEC-05

Which examples are captured

Authorityproposed
ChoiceOnly output of codeArbiter's deterministic tools (hooks, writers, scaffolder, release derivation, statusline); user requests and model narration stay labelled illustrative.
RationaleModel output is not reproducible; capturing it would claim proof the site cannot keep.
Source refNot yet supplied
DEC-06

How the Academy stops duplicating guides

Authorityproposed
ChoiceKeep the curriculum's required Understand the mechanism section and shorten it to a summary plus a link to the canonical page, through an arbiter-academy pull request.
Rationaleacademy_engine/curriculum.py requires the section; removing it would break the Academy contract for no reader gain.
Source refNot yet supplied

Sections

SEC-SMARTS

SMARTS design rationale

Blocks

Merge direction (DEC-01). Alternatives: A, command URL canonical with skill redirects; B, skill URL canonical; C, keep both pages and cross-link. Maintainable favours A and B over C, which keeps two hand-written texts per workflow. Available favours A: readers type the command. Testable is equal; redirects are checked by a config test and the link audit. A chosen.

Capture freshness (DEC-04). Alternatives: A, hash-bound committed captures with a gen-time check; B, regenerate captures in CI and diff. Reliable and Testable lean to B, which also catches output changes with unchanged sources; A catches source changes only. Securable and Available favour A: B adds a CI step that executes hooks in the docs job and lengthens it. Load-bearing assumption for A: captured output depends only on the hashed sources and the fixture. A chosen; B stays a follow-up if a capture ever drifts without a source change.

Academy duplication (DEC-06). Alternatives: A, shorten the mechanism section to a summary and link; B, delete the section; C, leave lessons and only add links. B breaks the curriculum contract; C leaves the duplicated teaching. A chosen.
