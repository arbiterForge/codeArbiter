Automatic tracker coordination for ordinary work transitions

Record local progress and configured tracker intent together; transmit explicitly through existing GitHub machinery; one independent tester-agent pass.

D01

Outcome: one local action, truthful coordination

Blocks

When an already-authorized agent starts, completes or reopens selected native work, the engine records that progress and the configured tracker intent in one local transaction. The model does not separately translate status names, stage issue state, stage Project fields or manage request hashes for each destination.

References: S01 S02 S03 S04

The transition does not perform network I/O. Explicit synchronization remains the transmission boundary. Local completion, checks, delivery and tracker observations remain separate facts. A provider outage is not a failed implementation and is not a reason to re-run reviewers.

References: S01 S02 S03 S04

This is the next increment after merged PRs #1069 and #1073. Do not rebuild native-first enrollment, adoption, work IDs, Projects transport, derived views or brownfield acquisition. The packet describes proposed behavior; it does not implement it.

References: S01 S02 S03 S04
D02

Keep the first delivery narrow

Blocks

Support three existing lifecycle actions: start → active; complete → complete; reopen → active. Map a transition only when its native state change is actually valid. Retain current refusal for an invalid second transition; an exact request retry uses journal replay rather than minting another event.

References: S01 S03 S04

Support a bound GitHub issue open/closed state and at most one configured Project single-select field. Reuse the existing issue/item binding. Missing bindings yield a durable waiting reason, not issue creation, automatic adoption or a partial local failure.

References: S01 S03 S04

Creation, issue publication, Project attachment, archive/deletion, assignees, labels, free-text fields, cycle-wide bulk updates, new providers and arbitrary rules are out of scope. Existing manual operations remain available. No new database, daemon, workflow language, embedding service, permission broker or background polling.

References: S01 S03 S04
D03

One finite, explicit project mapping

Blocks

Add a small separate mapping document, proposed path .codearbiter/work/transition-map.json. Do not add keys to the existing strict four-key project identity or rewrite provider.json merely to enable mappings. Absent/disabled mapping preserves existing behavior byte-for-byte where possible. Existing provider configuration alone never opts a project in.

References: S02 S03 S06

Configuration records project ID, issue and optional Project binding generations, one field ID, and fixed values for start/complete/reopen. A null target means no action. Use real discovered node/option IDs, never infer IDs from labels such as Done. The mapping is data, not executable commands or an authorization source.

References: S02 S03 S06

Configure or disable with a native CAS-checked operation through work.py. Resolve field options with current provider tooling when the owner sets up the mapping once. Offline configuration must not claim options were remotely verified. Preserve host/provider permissions and approved destinations; never put tokens in config, records, HTML or logs.

References: S02 S03 S06

Changes do not backfill old tasks or reinterpret pending effects. A configuration generation is frozen with each transition. A changed destination or generation requires explicit reconciliation/rebinding of affected intent, not silent retargeting.

References: S02 S03 S06

Bound the mapping to 16 KiB and three transition entries, with at most the issue-state and one Project-field target per entry. Bound live coordination metadata to 4 KiB excluding the existing native envelope. Reject oversized configuration on save; do not scan the project or tracker to interpret a transition.

D04

Extend the native transition, not a Python chain

Blocks

Refactor shared effect-staging logic into pure builders used by both manual and coordinated native operations. Do not call work-update, then stage-status, then stage-field as three separately committed operations: interruption would leave progress saved without its intended coordination.

References: S01 S02 S03 S06 S10

Under the existing exclusive store/CAS boundary, validate the selected work preimage, apply the legitimate transition, snapshot the applicable mapping, and stage each eligible effect or record its bounded waiting/conflict reason. Render once and commit the updated canonical work record once with the existing journal. No lock is held across network I/O.

References: S01 S02 S03 S06 S10

Unconfigured mapping is a no-op. Malformed optional mapping, missing credentials, unbound targets or stale provider generation must not erase legitimate local progress: store a truthful bounded coordination diagnostic and leave external effects untouched. Invalid work/CAS, unsafe store/journal or failed local persistence remains a real failed write. Never report saved progress after an I/O failure.

References: S01 S02 S03 S06 S10

If the current closed schema cannot represent the new metadata, use the repository’s capability/version mechanism. Do not insert unrecognized fields under an old format while promising old readers can still write it.

References: S01 S02 S03 S06 S10
D05

Minimal durable state, no general event queue

Blocks

Keep the existing provider_effect and project_effect as the only active send attempts. Add one bounded coordination record on the work item: latest source-transition ID, action, mapping generation/snapshot, source bindings, desired targets, target disposition and references to materialized intent IDs. This is pending intent, not a second task-status ledger.

References: S02 S03 S06

Derive a deterministic transition ID from the project/work identity and original durable operation identity plus the accepted transition generation. Each materialized effect has its own immutable exact intent ID linked to that transition. A repeated identical request returns the original result. A later same-looking completion has a different ID. Title edits and unrelated check records do not invalidate the intent.

References: S02 S03 S06

Do not silently discard a pre-existing manual pending effect. Do not replace any outcome_unknown attempt, even when the desired result has changed. Preserve that attempt; keep at most the latest desired target alongside it and expose waiting_for_reconciliation. Historical superseded details already live in committed state/journals; do not add an unbounded queue.

References: S02 S03 S06

The merge anchor is the frozen coordination intent, not late transmission bookkeeping. A mapped low-level effect names the source-transition ID and target ID and proves its exact desired value/destination derives from that saved source. Remote baseline observations and send-attempt IDs may be added after merge without requiring another commit merely to prove those observations. Never use that allowance to change the intended target or generation.

References: S02 S03 S06

An unsent mapped intent owned by an older transition may be coalesced to the latest mapped state under CAS only when it has no send claim. Invalidate its old intent for future sends and preserve a concise superseded reference. A stale clone cannot use an old merged intent to send a newer action. Cross-clone disconnected writes are not distributed exactly-once.

References: S02 S03 S06
D06

Sequence and conflict rules

Blocks

If start is followed by complete before synchronization, the Project need not briefly move to In Progress before Done. Coalesce only unsent intents generated by this mapping. If completion is followed by reopen while a close attempt is outcome_unknown, save local reopen, preserve the uncertain close, and retain the latest desired open/active target. Reconcile the old attempt before materializing a later one.

References: S01 S02 S03 S05

After uncertain success is reconciled, read current observations before producing the latest target. Do not automatically resend the old intermediate state. A manual remote edit that differs from the saved baseline remains a conflict, not an excuse to overwrite the human.

References: S01 S02 S03 S05

Already-known synchronized values equal to the target are no-ops based on the recorded observation, not a fresh remote-success claim. If the remote has since changed, the next explicit synchronization surfaces that fact. Same-state new requests follow existing lifecycle semantics; do not loosen them just to make testing easy.

References: S01 S02 S03 S05

An explicit manual change may supersede an unclaimed mapped intention under the existing requested operation, recording which intent was replaced; it never overwrites an uncertain claim. Automatic coordination subsequently reports manual ownership/conflict rather than reinstating its old value. Do not turn ordinary manual control into a second confirmation-code process.

References: S01 S02 S03 S05

Disabling the mapping stops new automatic staging. Existing manual/uncertain effects are preserved. Pending mapped effects become visibly paused and are not sent by the mapped path until explicitly resumed or cancelled. Disabling does not undo remote changes. A low-level command cannot bypass the paused/timing rules of a mapped effect merely because it is a different entry point.

References: S01 S02 S03 S05
D07

Remote sending stays explicit

Blocks

Keep current work.py sync and Project commands backward compatible for existing manual effects. Add one explicitly named high-level operation, proposed work.py sync-mapped WORK-ID [--pull-number N], to coordinate only the mapping-owned targets for this item. It is a convenience over existing senders, not a new transport or authority service.

References: S04 S05 S07

This new command explicitly requests Issue and configured Project synchronization. It must be explained by the help/output before use; do not silently broaden the old issue-only sync command. An invocation under existing user authorization is enough; no approval token or repeated per-field prompt is added.

References: S04 S05 S07

For mapped targets, inherit the provider’s after_merge timing by default for both issue and Project mutations. Require the exact staged transition/intent in the observed merged default-branch work record and current selected default-branch state. Never count an older PR containing equivalent text. Current low-level manual Project sync-now semantics remain unchanged for manual effects; mapped effects carry their timing fence wherever sent.

References: S04 S05 S07

An explicitly selected immediate provider still requires an actual authorized sync invocation. Neither complete nor a status/read/view hook sends anything. No watcher is created, and no promise is made that merging a PR alone causes an update. A later authorized finishing/sync workflow may call the mapped operation using the actual merge identity.

References: S04 S05 S07

Clarify ADR-0045’s distinction between manual explicit Project sync-now and this stricter mapped subset through normal documentation/decision ownership. This design does not silently mark a new ADR accepted or relax the default merge requirement.

References: S04 S05 S07
D08

Observation and partial results

Blocks

Issue staging reuses the last recorded verified issue identity/state. Project field staging must not invent a remote baseline just because local progress changed. When there is a stored field observation, compare against it on the next explicit sync. An absent observation is awaiting_observation, not a null-field observation.

References: S03 S05 P01 P02

During explicit mapped sync, obtain only the exact bound item/field observation needed. For a first observation, record that provenance and use the currently authorized target mapping; never claim it proves what the field was before. On later cycles, a mismatch with the retained baseline is a conflict. Preserve the existing read-before-send and readback behavior.

References: S03 S05 P01 P02

Materializing an awaiting-observation target does not mint a new high-level instruction or require a second local completion. If the original transition lacked the issue/item identity, later explicit binding may resolve it only with the existing verified work-correlation and unchanged frozen destination. A different issue, Project, field, option or configuration is a new intent, not a repair. If exact intent cannot be established, report that specific unresolved target.

References: S03 S05 P01 P02

GitHub Projects single-select mutation has no promised transactional compare-and-set. A human can race between read and mutation. Disclose that inherited limitation; do not claim perfect lost-update prevention, automatic rollback or a fresh approval scheme to hide it. Readback/application errors remain significant even with HTTP 200.

References: S03 S05 P01 P02

When issue synchronization succeeds and the Project fails, preserve issue success and retry/reconcile only the outstanding target. A grouped command returns target-specific outcomes. A remote failure never reruns the local lifecycle transition or promotes an unknown check to passed.

References: S03 S05 P01 P02
D09

Boundaries and UI

Blocks

Keep local progress, recorded checks, PR delivery and tracker coordination as separate facts. The saved work view should say “Implementation complete; issue close staged; waiting for merge” rather than “Done everywhere”. Update the existing render/context summaries, not a new dashboard application.

References: S01 S04 S07

Keep meaningful actionable reasons: mapping disabled/unusable, missing binding, awaiting observation, manual conflict, waiting for merge, uncertain outcome, partial synchronization. Do not force the model to inspect every raw hash to understand the next action. Retain exact IDs in details and machine responses.

References: S01 S04 S07

Existing source/plan freshness checks and exact retry semantics remain. A tracker bookkeeping update alone must not trigger a reviewer fleet or invalidate unrelated code verification. Reads, lists, context and saved-view generation stay local and do not stage intent.

D10

Compatibility and finite rollout

Blocks

No mapping is installed by default by enrollment or upgrade. Projects not opted in, native projects without a provider and selected legacy boards keep their current behavior. The new coordination feature is native-only initially; legacy lifecycle actions still work and configuration reports unsupported for that owner instead of silently adopting.

References: S02 S03 S06 S10

Do not migrate the primary repository or fix unrelated duplicate legacy origins just to exercise this feature. Use disposable local repositories. Keep portable pending coordination in canonical work; local .artifacts metadata is not its only copy. Git history does not preserve local journal before-images.

References: S02 S03 S06 S10

Public/embedded schemas, generated types, helper copies, native candidate packages and capability detection must move together. A new client reads old manual effects without inventing intent IDs; old readers of new unsupported records must refuse safely rather than discard fields. Rollback before new writes may restore compatible configuration; after new writes use forward recovery/export with current code.

References: S02 S03 S06 S10

Turning the feature off is not evidence that the record format is old-client-compatible. Do not restore an earlier work file over newer edits or imply that a Git revert reverses a remote mutation.

Blocks

The tester runs the real installed interface and adversarial cases, reports evidence and limitations, and does not modify production code or authorize release. There is no mandatory reviewer fleet and no runtime “tester approval” requirement.

First run a small current-release or source-candidate baseline journey to learn real behavior. Then unit/transaction and adapter faults, installed candidate checks, one model-driven fresh-project/resume journey, and an explicitly authorized remote readback. SEC-SMARTS

SMARTS design rationale

Blocks

Use a finite opt-in map and one native journaled mutation, retaining explicit existing GitHub senders. Chained mutations risk partial local results; a general queue or daemon adds authority and failure modes. The finite map preserves offline progress and manual control, while the Projects API still has no remote CAS.
