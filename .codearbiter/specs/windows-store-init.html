Explicit store initialization for fresh checkouts

A host can create a fresh checkout's local artifact store on purpose, so resume works on Windows while reads stay non-mutating.

Intent

CallerHost bridge ArtifactClient on Claude Code, Codex and Pi
OutcomeThe first read in a fresh writable checkout succeeds after one explicit, bounded store initialization; read-only checkouts still get NO_LOCAL_STORE.
ProblemOn Windows, every read in a fresh clone or worktree returns NO_LOCAL_STORE until something writes, so /feature and /sprint resume cannot read their own spec and plan.

Approach

Binding decision refs

ChoiceAdd an engine init-store operation that creates only the store lock metadata through the existing writer lock; the bridge calls it once on NO_LOCAL_STORE and retries the read once.

SEC-SMARTS

SMARTS design rationale

Blocks

Alternatives: A, the engine read creates the store (closed PR #998); B, keep reporting NO_LOCAL_STORE only; C, an explicit init-store operation with a one-time bridge retry.

Decisive lenses: Securable and Reliable favour B and C because no read ever writes; Available rules out B because resume fails until a write. C keeps both.

Material Weak observations: A is Weak on Securable (gives read-only reviewers a write path) and Maintainable (reverses #996's protocol text). B is Weak on Available.

Load-bearing assumption: the host process that constructs ArtifactClient is permitted to write untracked files in the checkout whenever it is not a protected read-only context; where it is not, init-store fails and NO_LOCAL_STORE stands.

Non-SMARTS considerations: C adds a public protocol operation, so it ships in a new plugin version.

Priority evidence: #972 chose Securable over Available for read paths; C honours that ordering without giving up Available.
