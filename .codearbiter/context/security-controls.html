CON-003

Secret store and access method

constraintsource-observed
Related refsNone recorded
Scope
PathsNone recorded
Source refs
  • SRC-001
Statement## Secret store and access method This project has no runtime secrets vault. Secrets belong in the owning process's approved environment or release secret store, never source, logs, artifacts, prompts, configuration commits, or diagnostic echoes. `FARM_API_KEY` is allowed only as farm runtime input. Sandbox `CLAUDE_CODE_OAUTH_TOKEN` injection is explicit `--with-claude` behavior; do not mount credential material with untrusted source or silently widen egress. The approved environment may be the owning process's secret source or the bounded runtime transport from its release store. Environment access by itself grants no new origin, sink, child, or lifetime permission. Keep each value within the owning process or the specifically approved child flow for its actual workflow lifetime, then release it; do not cache or serialize it for later work. Pi's ADR-0019 parent inference broker supersedes stored-provider credential projection. A child receives a short-lived per-child loopback token, not reusable provider credentials. The selected provider/model is exact; unavailable service must not cause automatic fallback. This is cooperative same-user isolation, not an OS security boundary: another local process holding the child token may use it until revocation. The broker closes and temporary state is cleaned on completion/failure. Secrets do not enter child argv or diagnostic output. Child provider configuration is credential-blind and schema-bounded. Only approved keys/shapes and pure environment references for API-key/header fields are projected; executable `!` values and unsupported provider/OAuth routes fail closed. Endpoint URLs exclude userinfo, query and fragment. Preserve bounded case-insensitive route validation. Child OS environment is minimal, excluding farm/Claude credentials; home, agent and session state are isolated, prompts use stdin, and `PI_PACKAGE_DIR` exposes only the intended parent package resources. Dummy-credential tests must not read real home authentication.

Network and untrusted execution

constraintsource-observed
Related refsNone recorded
Scope
PathsNone recorded
Source refs
  • SRC-001
Statement## Network and untrusted execution TLS verification stays enabled. API endpoints use HTTPS except narrowly bounded loopback test/broker paths. Farm validates its resolved base URL and each fetch, rejects userinfo and redirects, and emits origin-only diagnostics. Provider response bodies must not be copied into reports, retry messages or stderr. The update notifier makes bounded unauthenticated GitHub release reads without repository content, PII or credentials: at most ten pages/1,000 results, daily per-host caching, standard-library verified TLS, and fail-silent asynchronous behavior that does not add SessionStart network latency. Sandbox containers use non-root UID 1000, `--cap-drop ALL`, read-only root, `no-new-privileges`, resource caps and no privileged mode or Docker socket. `mounts.ts` is the single mount constructor: named volumes/tmpfs only, no host bind mounts. Network is offline by default and an unknown policy is an error. Clone inputs are bounded to approved HTTPS/SSH forms; reject leading options and transport-helper forms, preserve argv separation and `--`, and never interpolate untrusted input into a shell. Installed nixpacks detection does not authorize downloading/installing a helper at runtime. Container image inputs are digest-pinned; supply-chain tests reject floating `latest` inputs.

Sanctioned marker producers are cooperative attestations; never mint a marker, approval source or test/review result without its actual underlying action. A tool name alone does not prove coverage.

Statement## Native artifacts and recovery The native engine is pinned to the installed package's manifest/digest/platform qualification. Never discover a replacement on PATH or fetch one at runtime. Packaging/installers retain their platform-specific safe-path, no-follow and identity boundaries. Static source or fixture tests do not establish installed host permissions. The issuer re-binds run, source, module, platform, toolchain and bytes. Bounded requests/reads, stable IDs, exact revisions, safe HTML escaping, transaction journals, before-images, operation replay and no-follow filesystem checks protect data integrity. Progress and reported checks must remain separate from assessed evidence. A failed/flaky later result must remain visible. Reconciliation cleanup cannot erase a captured real stop because the capture preceded attempt persistence; recovery reuses the existing immutable observation and source, original operation ID and revision binding. Ambiguous/missing inputs stay unresolved without inventing authority. Migration/rollback preserves later work and complete-store history; it is explicit, not an automatic rewrite.

Published tag immutability

constraintsource-observed
Related refsNone recorded
Scope
PathsNone recorded
Source refs
  • SRC-001
Statement## Published tag immutability The four installable release series are `v*` (ca), `ca-sandbox-v*`, `ca-codex-v*` and `ca-pi-v*`. Consumers pin tags as payload identities. **A published tag is immutable: there is no break-glass.** Moving, retargeting or deleting one is prohibited for every actor, including administrators. Correct a bad release with a new version. This preserves the maintainer's 2026-07-25 ruling on issue #386; no standing bypass credential is justified by a recovery action the project expressly forbids. A mutable tag can redirect a pinned install to unreviewed code while its old release notes still imply the reviewed payload; deletion breaks availability. Preserve the two independent controls: 1. Repository tag rulesets prevent deletion and non-fast-forward movement over the release namespaces, without bypass actors for this immutability control. Rulesets are external settings, not source files; a historical setting snapshot does not prove current configuration. 2. `.github/scripts/check_tag_immutability.py` detects drift against the disjoint union of `.github/published-tags.json` (original-publication receipts) and `.github/legacy-published-tags.json` (closed historical baselines). The `[CHECK] | [REPO] | Published tag immutability` job is read-only. Detection cannot prevent an install between a ref change and the next audit, so it does not replace the preventive ruleset. The original-publication ledger retains both the tag object and peeled commit. A current API ref or mutable Release `target_commitish` cannot reconstruct a lost original identity. Ledger integrity rests on reviewed Git history and protected-main updates; changing a recorded identity to silence a red drift check is never a repair. Authenticate the original publisher run/artifact before reconciliation, bind its expected identity independently, and preserve uncertainty when that evidence is unavailable. A retained receipt is not a completed ledger handoff: only its reviewed addition merged to main completes ingestion. ADR-0034 fixes the legacy epoch at **44 records observed at `2026-09-04T20:45:43Z`**. It is **not original-publication proof**: a historical ref could have moved before observation. Its canonical identity-and-grade digest, source-matrix digest, timestamp, record count and **15/28/1 evidence-grade distribution** stay bound. The baseline provides forward detection only. Publishers and receipt reconcilers cannot grow the closed set. Adding or replacing an identity, source or grade requires a **new accepted, user-attributed ADR and architectural review**. Later tags use original-publication receipts; none may be relabelled as legacy to clear a failure. There is no break-glass for deletion, retargeting or movement; correction remains a new version. ADR-0040's accepted exception is narrow: required CI and the release workflow's preflight run without `--require-recorded`. A recorded tag that moved or disappeared, or invalid/unreadable inventory, still fails; an unrecorded new tag warns. Do not describe either workflow as strict missing-receipt enforcement. The checker still supports an explicitly selected `--require-recorded` audit; that capability is not evidence that every caller selects it. Receipt reconciliation remains separately authenticated and reviewed. Publication and ledger-PR merge are not transactional, and a later publication can race an already-green check. Preserve the accepted provenance-warning residual rather than inventing original-publication evidence or bypassing a drift failure.

ca-pi npm publication boundary

Statement### ca-pi npm publication boundary Pi publication of `@arbiterforge/ca-pi` uses npm trusted publishing with short-lived GitHub OIDC credentials. The npm package setting must authorize `arbiterForge/codeArbiter`, workflow filename `release.yml`, and `npm publish`. The GitHub-hosted Pi release job has `id-token: write`; no `NPMJS_TOKEN` or `NODE_AUTH_TOKEN` enters the publish invocation. An unavailable trusted publisher fails publication closed. The exact-byte integrity, npm audit signatures, and attested repository, workflow and source commit are blocking before the GitHub Release becomes public (ADR-0044). The exact npm@11.19.1 CLI is acquired without credentials over verified non-redirecting TLS, with pinned SHA-512 SRI, bounded regular contained archive extraction and a verified temporary CLI; never a global install or PATH replacement. Pins and the scoped registry are verified; install/pack/publish scripts are disabled. The credential-free download is exactly `https://registry.npmjs.org/npm/-/npm-11.19.1.tgz`, bound to `sha512-ztsxKxt/kkIaAs+2i0GU6I+DRmUdrNasxTZKJe9TCdSjKxlhah/4r/hl5ygMD6XAg1qZ9c2TNomR4qgOydp10g==`. Archive path-containment and the resolved executable are verified before use. `npm audit signatures` and SLSA checks bind source, builder, payload and commit; OIDC provenance is the approved publication identity. The npm trusted-publisher setting is managed in the npm package account; no token fallback is permitted. Pin changes need fresh review. Codex distribution uses the protected `codex-distribution` environment's six named values: `CODEX_DISTRIBUTION_APP_ID`, `CODEX_DISTRIBUTION_APP_INSTALLATION_ID`, `CODEX_DISTRIBUTION_APP_PRIVATE_KEY`, `CODEX_RULESET_VERIFIER_APP_ID`, `CODEX_RULESET_VERIFIER_APP_INSTALLATION_ID`, `CODEX_RULESET_VERIFIER_APP_PRIVATE_KEY`. Do not fall back to arbitrary repository/org secrets or local files. The separately user-authorized initial Codex npm organization token remains a recorded broader exposure/unknown-privilege residual; do not falsely describe it as environment-narrowed. The authorization for the first `@arbiterforge/ca-codex` publication recorded that the token was available to all organization repositories, with unknown npm privilege scope. Preserve that attribution; it is not a claim that the current deferred Codex publication workflow receives the token. When that authorized boundary is exercised, expose NODE_AUTH_TOKEN only in the authenticated publish step. Public cold install uses token-free npm configuration and exact retained package bytes; publication and channel advancement still require their owning checks. Publisher and verifier Apps have distinct positive IDs and process environments. Publisher: Actions read, Contents read/write, Metadata read, sole non-admin ruleset bypass. Verifier: Administration read/write and Metadata read, no Contents write and no bypass. Ordinary GITHUB_TOKEN stays read-only except the specifically owned Pi release job's Actions-read/Contents-write scope for draft Release access. Temp private keys use restrictive permissions, short-lived SHA-256 JWTs, verified TLS API calls and exit cleanup; only masked token outputs cross the intended step handoff. Job-scoped OIDC availability to all steps is an accepted residual, not a step-local capability. Release-target rows declare `pre-tag`, `rebuild`, `generate` and optional `release-build` as operator-authored executable inputs, length-capped to 1,024 characters. Release hashes bind the ordered `pre-tag` list plus `release-build`, `rebuild` and `generate`; changing any one invalidates the per-target confirmation. Read every declared executable input before recording that confirmation, and check it before the first executable declaration runs. Dry runs only list the commands and never mint a durable confirmation. `pre-tag` is check-only and mechanically guarded by `run-pre-tag`. The reviewed hosted-build path runs `release-build` only in the exact-candidate publisher, with a newly empty `RELEASE_ASSET_DIR`, a clean tracked tree before and after, and exact asset-inventory verification. The alternative retained-cohort path treats its exact fail-closed sentinel as policy, never as a locally runnable builder. It accepts only retained CI packages whose digests, receipts, source commit and flat names bind to the exact candidate; arbitrary build failures cannot select this exception. H-22 protects the declaring file with its actual authoring marker. This remains a cooperative governance boundary, not shell sandboxing or filesystem confinement. Package identity, deterministic contents, registry ownership, provenance and public cold install are verified before marketplace promotion. Preserve explicit publication authorization and exact distributed-byte readback.
