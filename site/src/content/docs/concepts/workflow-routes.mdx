**The same parts do not imply the same procedure.** A feature, a sprint, a decision and a
release can all involve review, yet their callers, records and stopping points differ. Start
with the result you need, then trace the handoff that produces it. Do not run every command
in a diagram as a checklist.

## Workflow atlas

Choose a map tab, then **Trace an entry** to highlight its nodes and connecting arrows.
Selecting an entry keeps the current map in place, so you can compare routes without losing
the surrounding context. Select a node to inspect its explanation and pinned sources beside
the diagram. **Clear** restores the complete map.

**Fit width**, **Fit all**, **Read size** and the zoom controls change the canvas scale.
Drag blank space to pan, or use the scrollbars. **Context layers** shows how governing inputs
reach each participant; execution, context, conditional and return arrows remain distinct.
**SVG ↓** saves the complete editable map, not just its highlighted portion.

## Keep your place in a route

In the atlas, **Link to view** preserves the selected map and highlighted entry. After a
node selection it links to that node. Tab and entry controls alone do not write browser
history. Explicit links use ordinary fragments; Back, Forward and reload restore them.
**Text routes** opens the complete reading path without replacing the interactive map.

In the existing chapter maps, **Next chapter** and **Previous chapter** let you continue
without scrolling back through the explanation. **Link to this chapter** gives that chapter
an ordinary browser address. Following it reveals the requested chapter and opens its
enclosing disclosures, including the appropriate initialization alternative. Keyboard focus
follows an explicit chapter link into the requested chapter.

Chapter buttons only change the reading view. Explicit chapter links change the address fragment,
so browser Back can return to the earlier linked chapter. No bookmark or progress record is saved.
Without JavaScript every chapter remains in the document; open its native disclosure to read it.
Printing includes the full path, not only the selected chapter. Reaching the end of the diagram
means you have read the route, not performed or approved the work.

## Read the arrows, not only the rows

**Commands** are entries or caller-owned procedures. **Skills** own procedural work.
**Agents** perform bounded roles. Those are three participant types, not three consecutive
phases. In the chapter maps, read the numbered steps left to right, then continue to the
next chapter. A handoff can cross rows and return to its caller. The horizontal dotted row
is a visual guide, not an executable connection among every item on that row.

A dashed reuse arrow in a chapter map means the current caller performs an existing procedure
without invoking its entry again. In the atlas, consult the side-panel legend for execution,
context, conditional, return and stop relationships. Conditional reviewers participate only
when their source contract selects them. Return paths preserve task repetition, correction
and user decisions. An empty role row is intentional when the owning route names no participant
of that type. It is better to show the absence than invent an agent to make a diagram look balanced.

Arrowheads mark directed handoffs, not completion, success or approval. None of the diagram
controls runs a command or records a workflow transition. On narrow screens, **Read size**
keeps the atlas legible in its panning canvas and **Details ↓** reaches its inspector.
The complete text path remains available rather than requiring a shrunken image.

## Boundaries that change the route

**A sprint is not an attended feature with fewer pauses.** Its initial HTML pair can use one
qualified, host-observed pair transaction. Its approved plan goes directly to the task engine
without the attended batch coordinator. Security, authority and other named hard gates still
stop; autonomy ends at the PR, not a merge. Existing Markdown and later single-artifact changes
retain their own contracts.

**Dependency review is not installation permission.** The command sends adoption review directly
to its reviewer, gets the verdict back, and then asks for the exact installation confirmation.
One-time tool inspection has separate eligibility conditions; it does not silently become a
project dependency. Neither route is execution isolation or an unconditional safety guarantee.

**Acceptance is not delivery.** An ADR begins Proposed. Explicit acceptance, reviewed obligations,
committed content and a subsequent acceptance binding establish a narrower claim than current
implementation or verification. Status inspection and optional challenge are separate operations.

**A release has a mandatory PR boundary.** The interactive preparation commits release surfaces,
reports asset names and the declared publisher, opens the release PR and stops. Only a qualifying
hosted publisher at the exact merged and verified default-branch commit can compose the tag.
Publication still needs its applicable one-cohort authority, and any declared provenance closeout
uses a separate receipt PR. A dry run neither executes that sequence nor proves its checks passed.

**Initialization has alternatives, not a longer universal chain.** Greenfield work interviews you,
produces the three architecture/planning documents, obtains their approval and populates context.
Brownfield initial or full work requires six logical category reports from a qualified,
host-enforced read-only context scout profile. A scoped refresh covers only its affected
categories and cannot claim a new full scan. The current generated host surfaces lack that
qualified profile, so this route stops before dispatch. If qualified, the route synthesizes
source evidence, resolves or defers gaps, and binds derived context to its sources. Neither
initialization route should be drawn as completed implementation, and brownfield does not
retroactively invent the greenfield roadmap.

## Use the map to inspect a real handoff

Name the selected route, the current artifact or source identity, the caller and its next action.
Ask what comes back and which condition permits continuation. A stopped step needs its own
missing fact, decision or fresh evidence; a later green status does not replace it.

These diagrams are **current-source explanations**, not recorded executions or certifications
of an installed release. Each map names its reviewed commit and owning sources. Consult the
[installed-host authority boundary](/guides/review-artifacts/#check-your-hosts-authority-capability)
before relying on typed behavior. Keep an unknown capability visible rather than substituting a
different format or inventing a receipt.

For the ordinary commit/PR handoff, use [Review and ship](/guides/review-and-ship/). For interrupted
state, use [Resume and recover](/guides/resume-and-recover/). For the difference between accepted,
implemented and verified decisions, read [ADRs and their evidence](/concepts/adrs/). The existing
[Concept Map](/concepts/) remains the starting point for the connected product model.
