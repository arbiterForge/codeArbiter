Greenfield means the project has no meaningful source to inspect yet. codeArbiter therefore starts
from your intent, not a guessed architecture. The interview's central deliverable is a set of
**three project-planning documents**. It also populates the context that later work reads.

## Before entering the interview

Open the intended repository in your coding host. In a separate native terminal, run
`git rev-parse --show-toplevel` and `git status --short` to confirm its root and existing changes.
Changing a terminal directory does not necessarily change the repository open in the host.
Preserve any existing work. If there is meaningful source, use
[Understand an existing project](/guides/understand-an-existing-project/) instead.

Bring the problem, primary users, a concrete description of a useful first version, hard
constraints, and the things you explicitly are not building. A sketch or requirements note is
useful input, not something the agent should silently treat as approved truth. Do not supply
production credentials or confidential examples that the configured provider must not receive.

Describe the goal naturally, or use an explicit entry:

| Host | Start the greenfield route |
|---|---|
| Claude Code | `/ca:init --greenfield` |
| Codex | `$ca-init --greenfield` |
| Pi | `/ca-init --greenfield` |

`init` scaffolds the state store when needed and enters decomposition. The existing `decompose`
command remains a compatibility entry for that same strategy. An initialized project returns to
normal work; selected context changes use `context-check`. Meaningful existing source routes to
the brownfield populator. Neither case permits overwriting existing project records.

## Work through six areas

The interview covers vision and problem, users and flows, functional scope, technical shape,
integrations and infrastructure, then risks and unknowns. Existing answers and settled decisions
carry forward. Questions focus on missing facts and consequential choices; inapplicable areas
are recorded with their reason.

Answer in observable terms. Instead of “make exports work well,” identify who exports, what is
exported, the format, the empty case, and how a reviewer could tell whether it works.
codeArbiter challenges vague answers and explains architectural trade-offs. You own material
choices. A genuinely unresolved answer becomes an explicit `[CONFIRM-NN]`, not an invented fact.

At each completed layer, the interview writes its record beneath
`.codearbiter/plans/decomposition/` before starting the next layer. `_session.md` records the phase,
remaining questions and actual confirmations. User-decided architectural choices go through the
decision-lifecycle owner; draft choices remain drafts until actually decided. **Do not assume
every unfinished answer has already been saved.** Before leaving, inspect the retained records.

## Review the three deliverables

After all six layers are complete, codeArbiter re-reads the saved records and writes:

| File under `.codearbiter/plans/` | Purpose | Review it for |
|---|---|---|
| `01-architecture-breakdown.md` | Components, responsibilities, connections, system diagram, integrations and open architectural questions | Missing owners, incorrect boundaries, hidden integrations and designs that do not represent your intent |
| `02-phased-build-plan.md` | MVP, v1 and v2 goals; included and deferred work; rationale, risks and measurable definitions of done | Whether the first phase is useful, deferrals are deliberate and each completion test is observable |
| `03-task-backlog.md` | Prioritized, phase-grouped work with role assignments, dependencies and time-boxed spikes | Whether work is estimable, dependencies are sensible and uncertainty is investigated rather than concealed |

Open **all three files** before approving. They are already on disk at this review boundary.
For the [saved-search example](/product-tour/#project-blueprint), ask whether CSV export belongs
in the first useful release, whether the export component owns formatting rather than storage,
and whether the backlog leaves an investigation for any unresolved external integration.

A useful revision request is: “The first phase must export existing saved searches, but must not
add account sharing. Update all three documents consistently and return them for review.”
Your actual confirmation covers the three documents and is recorded in `_session.md`. Existing
confirmation covers unchanged artifacts; corrections do not restart settled questions. A
consequential unresolved choice holds its dependent output, while other explicitly retained gaps
stay on the question board. Confirmation does not authorize later scope expansion or a merge.

## Understand the two planning scales

The decomposition backlog is **project planning**. A later feature's execution plan breaks a
selected change into coherent, verifiable tasks with actual dependencies. Choose task sizes for
useful progress and review. The two plans serve different scopes even though both live under `plans/`.

The three named greenfield documents remain Markdown. They are not legacy feature artifacts
waiting for automatic HTML conversion. New full-lane feature and sprint work has a separate
[typed specification-and-plan contract](/guides/review-artifacts/).

## Confirm initialization, then choose work

After confirmation, the populator derives context, stack, coding standards, security controls and
a planned code map from the retained inputs. Planned commands and paths stay labelled as planned
until actual source establishes them. The native writer's `--context-draft` and `--context-apply`
operations populate five document/provenance pairs together, preserving activation frontmatter.
Inspect each preview and its source bindings before applying it under the existing authorization.

Tasks are populated through their owning writer without duplicating existing entries. Questions,
decisions and audit history remain intact. `--context-finalize` validates the thirteen required
outputs: five document/provenance pairs, the task board, question board and audit log. Apply its
preview through the native writer to record the `<!--INITIALIZED-->` marker and matching context
provenance together. A failed or uncertain transaction needs its reported repair or recovery;
do not append the marker manually.

Read back the result, retain the interview, plans and decision history, and remove only temporary
drafts that no provenance source references. Report unresolved choices and observed checks, then
continue authorized work. Initialization records population; it does not establish accurate
implementation, passing tests or installed-host enforcement. Use
[Protect your first repository](/getting-started/quickstart/) for host qualification and
[Build a feature](/guides/feature-lane/) for the next selected change.

## Resume, revise, or reconcile

Re-entering decomposition after interruption resumes the first unfinished step from the retained
session and layer records. An explicit restart preserves earlier interview and decision history.
If interrupted records are in a temporary location, preserve them in the durable interview
directory before citing them as provenance sources. Reconcile conflicting versions without
overwriting either. Do not delete records to make the initialization check pass.

Later, when architecture, roadmap, backlog or prior decisions disagree, `reconcile` reads these
**exact three filenames**. It presents variances for your choice and records the outcome. It does
not silently rewrite the documents, fix code or create an ADR itself. A replacement ADR uses the
ADR lane. Preserve the filenames unless the owning product contract changes.
