Use an autonomous sprint when you can describe a substantial outcome and want codeArbiter to carry
the work through implementation, verification and a pull request without stopping between task
batches. Your request establishes the working scope. codeArbiter maintains a specification and
plan, asks about consequential missing choices, and continues within your stated limits. A sprint
request does not authorize merging or publication.

New HTML work uses the installed native writer on supported hosts. Its capability check protects
artifact integrity; it does not grant tool permissions or establish live-host qualification.
Explicit attestation has separate host support requirements. See the
[capability boundaries](/guides/review-artifacts/#check-your-hosts-authority-capability).

## Before you begin

- Start on a non-default branch or allow the sprint to create an isolated worktree.
- State the outcome, boundaries, and any spending or external-side-effect limits.
- Identify any unresolved user decisions the goal depends on; independent work can continue.
- Expect a maintained specification and implementation plan. State any review pauses you want.

Invoke the sprint with the outcome, not a list of implementation guesses:

```text
/ca:sprint "Add an export flow for saved searches, including empty-state behavior, audit records, and user documentation"
```

## The working spec and plan

codeArbiter investigates the repository and prepares two linked artifacts:

1. **Sprint spec:** the user outcome, scope, exclusions, acceptance criteria, and hard constraints.
2. **Implementation plan:** exact tasks, files, tests, dependencies, ordering, and verification
   mapped back to every acceptance criterion.

Read them together to see whether the plan covers the intended outcome. If planning reveals a
consequential missing requirement, codeArbiter asks its owner once and keeps the affected work
waiting. An implementation method, test runner or task breakdown can change within the agreed
outcome with a recorded reason. Neither file introduces a second permission interview.

## Inspect the durable package

New full-lane work uses `.codearbiter/specs/<slug>.html` and
`.codearbiter/plans/<slug>.html` through the installed native writer.
Existing Markdown pairs remain on their exact legacy path. Open both files and inspect the
criteria, exclusions, task coverage, dependencies and verification.
[Review specifications and plans](/guides/review-artifacts/) explains the distinction between a
browser view, structural readiness, implementation progress and actual evidence.

For the [saved-search example](/guides/first-feature/), a request for CSV export must not silently
include account sharing, external spending or publication. Request a scoped revision if the plan
misstates the outcome.

## Execution and resumption

The sprint executes coherent tasks through their actual dependencies:

1. read the selected task's criteria, relevant source and prerequisites;
2. select verification appropriate to the change;
3. implement directly or delegate a bounded unit when useful;
4. run applicable checks and obtain independent review where required;
5. record actual results, failures, unrun checks and implementation progress; and
6. continue independent work while affected blockers remain visible.

A confirmed bug needs a genuine failing regression before its fix. Feature work verifies the
selected criteria and reports the observed test sequence; a behavior-preserving refactor uses
passing characterization checks. Tests and review follow the work's obligations and risk.
Typed `REVIEW` means implementation is ready; `DONE` means implementation is reported complete.
Neither status certifies passing checks, independent review or user acceptance.

An interrupted session re-enters through the existing spec, plan, task states and sprint log.
Inspect running workers, partial changes and committed work before reconciling an `IN_PROGRESS`
task. Preserve user stops and do not redispatch an uncertain attempt because its reply was lost.
Recheck evidence affected by source or result changes; resuming alone does not require a new
reviewer fleet. See [Resume and recover](/guides/resume-and-recover/).

## How autonomous decisions work

The sprint makes reversible implementation decisions within the requested outcome. Use
[SMARTS](/concepts/smarts/) when a difficult trade-off warrants comparison across Scalable,
Maintainable, Available, Reliable, Testable and Securable. Material choices, their reasons and
meaningful uncertainty are recorded in `.codearbiter/sprint-log.md`.

Low-confidence decisions are called out in the pull request so you can review the places where the
evidence was genuinely close. Spending outside your stated limit is not treated as an ordinary
SMARTS choice.

Factual prerequisites can be checked through ordinary authorized tools. Record what was observed
and which tasks it affects. A tool result does not settle a user-owned product choice, and a SMARTS
recommendation does not authorize spending or a broader outcome.

## Stops that remain yours

Stop affected work for:

- an explicit user stop or requested review pause;
- a consequential missing product decision;
- a real host or tool permission denial;
- an applicable security, secrets, migration or publication control; or
- irreversible operations, overrides, external spending or side effects beyond existing authority.

Already-authorized security work does not automatically need another user reply. Resolve actual
risks and preserve required review. A failing test calls for diagnosis and correction, not a new
permission code. If one task is blocked, independent safe work continues.

## Pull request and verification

The normal sprint exit is a pull request, not a merge. The PR should contain:

- the maintained spec and plan;
- acceptance-criterion to task/test coverage;
- verification commands and results;
- reviewer findings and their dispositions;
- SMARTS decisions, with low-confidence calls highlighted; and
- remaining blocked, unverified or out-of-scope work.

Confirm the PR is draft when you want a deliberate merge barrier. Hosted checks still need to run
against the exact current PR head before the work is treated as ready.

## Optional farm backend

**HTML plans cannot use `--farm`.**
The following example applies only to an existing authoritative legacy Markdown pair. Do not
convert a new HTML plan to Markdown to make the flag work.

For that existing legacy backend, `--farm` selects a configured OpenAI-compatible worker:

```text
/ca:sprint "Normalize the public API error contract" --farm
```

The same working scope, applicable controls, checks, review and PR boundary apply. Farm use is a
separately requested preview backend requiring provider configuration, a budget and circuit-breaker
limits. Failure does not authorize a silent backend switch. It may transmit secret-redacted, byte-capped
task context to the endpoint you configure; read [Compatibility: Network Calls](/getting-started/compatibility/#network-calls)
before enabling it.

## Verify and review

After the PR opens:

1. read the acceptance criteria and plan delta;
2. review low-confidence SMARTS entries in `.codearbiter/sprint-log.md`;
3. confirm every required local verification is present;
4. wait for hosted checks on the exact PR head; and
5. authorize merge separately when the required evidence supports it.

For the exact orchestration contract, see the [`sprint` command](/reference/commands/sprint/) and
the [`subagent-driven-development` skill](/reference/skills/subagent-driven-development/).
