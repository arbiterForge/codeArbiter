A request, an implementation and a passing test establish different things. codeArbiter gives
each stage an owner. A **lane** selects the path for the work; **skills** define its procedures;
**agents** perform bounded author or reviewer roles. **Gates** require decisions or evidence before
the next transition.

Follow **who acts next, what they produce, and what permits continuation**. That is the mental model
behind the operating [guides](/guides/) and exact [reference](/reference/).

## Follow one change from request to PR

A saved-search export starts as an idea. Its specification defines ordering, escaping and empty
results. A plan maps those criteria to tasks. The implementation owner chooses direct implementation
or useful delegation, applies meaningful checks, and requests independent review where risk or
policy requires it. The coordinator reports progress and continues authorized work, respecting
explicit user pauses and real consequential decisions.

This map follows the full feature lane and its **Open a PR** exit. Rows identify roles; arrows show
execution order. TDD runs inside task authoring, and delegated work returns to its caller.

## Other workflows have different endpoints

Compare the [sprint, dependency, decision, release and initialization routes](/concepts/workflow-routes/).
Their maps preserve the same Commands / Skills / Agents language but follow each owning contract.
A release crosses a mandatory PR and hosted-publication boundary; initialization ends in context,
not a manufactured pull request. Role membership alone does not establish an execution sequence.

## Five connections make the model useful

**Work has a governing definition.** A feature specification describes observable behavior;
a linked plan describes how to implement and verify it. The project architecture and roadmap
operate at a broader scale. An item on the task board is not a substitute for any of them.

**A decision has a scope.** Clarifying product behavior, deciding architecture and authorizing a
merge establish different things. Keep the user's existing authorization and actual choices;
updating a plan does not itself require another permission reply. An accepted architecture decision
records a choice, while implementation and verification need their own evidence. SMARTS can help
compare genuine alternatives without replacing the decision owner.

**Context is selected, not guessed.** Repository policy, decisions and source-backed knowledge
inform the work that touches them. Provenance helps identify stale derived knowledge. Just-in-time
injection points a file read toward its relevant governing record; it does not load the whole
repository or prove compliance with every rule.

**Review is not authorship.** The coordinator selects useful work and relevant roles. The
implementer makes the bounded change; applicable reviewers challenge it under their own contracts.
The caller examines actual check results and their source scope. An author's summary cannot turn
an unrun check into a pass.

**Evidence names its boundary.** A local passing test applies to the exercised behavior and source.
A task marked `DONE` records implementation progress, not passing checks or independent review.
An explicit attestation claim needs its own actual evidence. A PR URL establishes an open
proposal, not a merge or deployment. An audit packet assembles the records available for its window;
missing records must remain visible as missing.

## A concrete example

Suppose the export request also introduces a new parser dependency. The feature lane still owns
the requested behavior. The dependency procedure governs the proposed package before installation.
The test obligations establish what the CSV must do. A security-relevant path can bring in its
controlling policy and applicable reviewers. These are related controls, not permission to replace
one procedure with another or dispatch every reviewer on every task.

If the parser decision remains unresolved, it is surfaced rather than hidden in implementation.
If the implementation fails a regression, the failure requires correction and a fresh run.
If a task is marked `DONE` but a required check is unrun, report verification as pending. Continue
independent authorized work while resolving the actual gap. Each problem returns to its owner.

The [worked first feature](/guides/first-feature/) has inspectable drafts and local test evidence.
Its illustrative conversation is deliberately separate from captured test results. Use it to see
the records, not as proof that the same execution occurred in your repository.

## Put the model to work

Name the next intended change, the record that defines it, the role that should act, and the
condition that permits continuation. Then identify what evidence you expect back and where the
lane stops for you. A reader who can answer those questions can choose a [guide](/guides/)
without memorizing an internal catalog.

For a blocked or interrupted installation, use [Troubleshooting](/guides/troubleshooting/).
For uncertain work state, use [Resume and recover](/guides/resume-and-recover/).
For hands-on practice with a separate verifier, use [Arbiter Academy](/academy/).
